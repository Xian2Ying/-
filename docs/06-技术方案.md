# 06 · 技术方案（移动端优先 + 双端数据互通）

> 状态：**待评审** · 日期：2026-10-30
> 前置文档：`docs/04-方案选型决策.md`（已选定小游戏为主载体）

---

## 一、用户的明确要求（原始约束）

1. **移动端优先**：先保证手机端体验与稳定。
2. **PC 端后做**：在移动端稳定之后再制作。
3. **两个都要**：不是"只做移动端"，PC 端是必交付项。
4. **资料、文件互通**：双端的数据/内容必须一致，不能各存各的。

---

## 二、核心结论

> **一套代码，响应式断点适配，数据层与视图层彻底解耦。**
> 移动端与 PC 端共享同一个 `core` 内核（词库、出题、判分、记忆调度、存档），
> 只在「视图层」做布局差异。

### 为什么不能写两套代码

| 做法 | 后果 |
|---|---|
| ❌ 移动端一套、PC 端一套 | 词库要维护两份、出题逻辑要改两遍、存档格式对不上；改一个 bug 要改两次；4 周内 1 个技术担当必然崩 |
| ✅ 一套代码 + 断点适配 | 内核只写一次；双端天然互通；PC 端适配只是"加样式 + 加键盘交互"，工作量可控在 8–12 小时 |

**「互通」的本质不是同步技术，而是架构问题**：只要两端都通过同一个数据入口读写，互通就自然成立。真正的坑是视图层直接碰存储（各写各的 `localStorage`），那数据必然对不上。

---

## 三、分层架构

```
┌─────────────────────────────────────────┐
│  视图层 View（双端差异在这里）           │
│  ├─ 移动端：竖屏 / 底部 tab / 拇指区      │
│  └─ PC 端 ：宽屏 / 侧栏常驻 / 键盘快捷键  │
├─────────────────────────────────────────┤
│  内核层 Core（双端完全共用）             │
│  ├─ 词库加载  ├─ 出题引擎                │
│  ├─ 判分逻辑  ├─ 记忆调度（艾宾浩斯）     │
│  ├─ 错题本    └─ 成就 / 金币 / 经验      │
├─────────────────────────────────────────┤
│  数据层 Storage（唯一读写入口）          │
│  └─ adapter：localStorage ⇄ 云端同步     │
└─────────────────────────────────────────┘
```

**铁律**：视图层不得直接调用 `localStorage`，一律走 `core/storage.js`。

## 四、双端差异清单（不是简单缩放）

| 项目 | 移动端（先做） | PC 端（后做） |
|---|---|---|
| 布局 | 竖屏单列，纵向滚动 | 宽屏双列 / 三栏，侧边栏常驻 |
| 导航 | 底部 tab（拇指区） | 顶部 + 左侧导航 |
| 触控 | 按钮 ≥ 44px，大间距 | 鼠标 hover 态，密集排布 |
| 关卡地图 | 纵向路径滚动 | 网格平铺，一屏看全 |
| 键盘 | 无 | 1/2/3/4 选选项，Enter 下一题，Esc 返回地图 |
| 信息密度 | 低，一屏一事 | 高，一屏多看（进度+词库+错题本同屏） |
| 离线 | 必须断网可玩核心关卡 | 同左 |

## 五、互通设计（三层）

### 5.1 数据互通 —— 用户学习数据跨端一致

| 数据 | 内容 | 优先级 |
|---|---|---|
| 学习进度 | 关卡解锁 / 通关状态 / 星级 | P0 |
| 词库掌握度 | 每词：对/错次数、熟练度、下次复习时间 | P0 |
| 错题本 | 错词 + 错误选项 + 时间戳 | P0 |
| 资产 | 金币、经验、连击、成就 | P0 |
| 学习报告 | 掌握度、薄弱章节 | P1 |
| AI 对话记录 | NPC 口语练习历史 | P1 |

**同步策略（本地优先 / 乐观更新）**

1. 写入先落本地 `localStorage` → 界面立即响应（不等网络）
2. 已登录 + 有网 → 后台异步上行到云端
3. 冲突解决：按 `updatedAt` 时间戳，**后写覆盖**（学习数据无需 CRDT）
4. 断网：操作进离线队列，恢复后补传
5. 登录时：云端 `updatedAt` 与本地比较，取较新的一方

### 5.2 内容互通 —— 词库 / 题库只有一份

- 所有内容以 **JSON 数据文件** 形式存在仓库：`src/data/words.json`、`src/data/questions.json`、`src/data/knowledge-cards.json`
- 两端从同一份文件加载，**不存在"移动端词库更新了 PC 端没更新"的问题**
- 内容官（队友 A）只改 JSON，不碰代码 → 内容与代码解耦，也不会改坏程序

### 5.3 项目资料互通 —— 三人 + 三个 AI 共享同一上下文

- `AGENTS.md` + `docs/` 是唯一事实来源
- 所有人的 AI 都把 `word-quest/` 作为工作区打开
- 决策变更后立即更新文档，所有人同步

## 六、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | 原生 HTML + CSS + JavaScript（ES Module） | 零构建、零依赖、双击即开；队友 B 无框架负担 |
| 游戏引擎 | **不引入** | 只有 1 个技术担当；本作是答题闯关，不需要物理引擎 |
| 响应式 | CSS `@media` 断点 + CSS Grid / Flex | 一套代码覆盖两端 |
| 像素渲染 | Canvas 绘制 + `image-rendering: pixelated` | 保证像素风不被模糊 |
| 存档 | `localStorage`（默认）+ 云端同步（加分项） | 匿名也能玩，登录才同步 |
| 云端（候选） | 腾讯 WorkBuddy 云服务（云数据库 + 用户认证） | 与比赛平台同源，故事好讲；**待验证能否在 H5 中直接调用** |
| 发音 TTS | 浏览器原生 `speechSynthesis` | 零成本、零依赖、离线可用 |
| AI 对话 | DeepSeek API（文字） | 成本低、中文友好 |
| 版本管理 | GitHub，仓库名 `word-quest` | 过程要求 |

## 九、风险与降级预案

| 风险 | 概率 | 降级方案 |
|---|---|---|
| 云端同步搞不定（无后端经验） | 中 | **L0 存档码方案兜底**：导出存档为一段文本码 / JSON 文件，另一端粘贴导入。零后端、零成本，真·互通 |
| PC 端来不及 | 中 | 移动端响应式在 PC 上本来就能打开（只是不优化）。PC 端是"锦上添花"，非生死线 |
| 词库内容不够 | 低 | 内容官提前备 120 词，多出 20 词缓冲 |
| AI 接口不可用 | 中 | NPC 切固定脚本演示；游戏本体不受影响 |
| 双端布局冲突导致返工 | 中 | 靠「视图层不碰存储」+ 共用内核规避；样式文件物理分离 |
